RISC-V Processor

A 5-stage pipelined RISC-V CPU, built from scratch in SystemVerilog over a semester of Computer Organization — one phase at a time, from a single-cycle datapath up through hazard detection, forwarding, branching, and full load/store support.

Role
Solo — individual coursework
Course
ECEN 3593 · Computer Organization, CU Boulder
Stack
SystemVerilog · RISC-V assembly · Icarus Verilog
When
Spring 2026

What it is

This is a RISC-V (RV32I) CPU implemented as a classic 5-stage pipeline — fetch, decode, execute, memory, writeback — built up in stages across the semester rather than all at once. Each phase added a real capability to a working processor: the base datapath and control logic first, then data hazard detection and forwarding, then branches and pipeline flushing on mispredicts, and finally full load and store instruction support.

Working incrementally on a single, continuously-running design meant every new phase had to slot into an existing pipeline without breaking what already worked — closer to how you'd extend a real CPU than a one-off assignment.

Load/store & hazard handling

The most recent phase added the full RV32I memory instruction set — lw, lh, lhu, lb, lbu, sw, sh, sb — which meant wiring a data memory into the memory stage, adding byte-enable addressing so the datapath could correctly read and write partial words, and sign-extending sub-word loads based on instruction type.

The harder half was hazard correctness: a load followed immediately by an instruction that depends on the loaded value can't be resolved through forwarding alone, since the data isn't available until the load reaches writeback. I implemented load-use hazard detection that compares the destination register of an in-flight load against the source registers being decoded, and on a match, stalls the pipeline for exactly one cycle — inserting a bubble and holding the PC and fetch/decode register — before resuming forwarding as normal.

Structure

The design splits cleanly across pipeline stage modules (fetch.sv, decode.sv, execute.sv, mem.sv, writeback.sv) wired together in cpu.sv, with a register file, ALU, data memory, and a testbench (system_tb.sv) rounding out the system. Control signals — memory write enable, byte-enable width, load type, register writeback source — are set in decode and carried down the pipeline registers stage by stage, which keeps each module's responsibility narrow and makes the datapath easy to trace when debugging.

Verification

Each phase shipped with hand-written RISC-V assembly test programs and documented expected register-file traces. I simulated the design in Icarus Verilog, diffed the actual register updates against expected output, and used waveform inspection to trace mismatches back to the responsible pipeline stage — the same debug loop you'd use on real hardware, just without the hardware.

What I learned

This was my first sustained hardware design project, and the biggest shift was learning to think in cycles and signals instead of sequential code — a stall, a flush, and a forwarding path all have to be correct simultaneously, every clock edge, with no room for the "run it again and see" debugging habits software lets you get away with. It also gave me a much more concrete sense of what a CPU is actually doing underneath every program I write.
